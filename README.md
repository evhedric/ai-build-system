# AI Build System

A local-first AI orchestration system where multiple AI models collaborate autonomously to plan, execute, and review work — without a human acting as a middleman.

---

## What This Is (and Isn't)

**This is:** An autonomous, file-based AI pipeline that takes a single task description and routes it through four specialized agents (Architect → Planner → Executor → Reviewer) until the work is complete. It is designed for code generation, file creation, and structured content tasks.

**This is not:** A general-purpose AI assistant, a real-time IDE plugin, or a production deployment tool. It does not run tests, validate generated code at runtime, or guarantee correctness — the Reviewer evaluates against structured criteria, not live execution. Human review of generated output before merging is strongly recommended.

**Why use this over a single LLM call?** Each agent has a narrow, specialized role backed by a tailored system prompt. The Architect enforces constraints before any code is written. The Reviewer closes the loop with structured pass/fail logic. This separation reduces hallucination drift and produces more consistent, reviewable output than a single large prompt.

---

## Overview

Submit a task once. The system routes it through four specialized AI agents, each with a distinct role, until the work is complete and approved.

```
User Request
     │
     ▼
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  Architect  │───▶│   Planner   │───▶│  Executor   │───▶│  Reviewer   │
│  (OpenAI)   │    │  (OpenAI)   │    │  (Claude)   │    │  (OpenAI)   │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
  Goals &            Ordered            Creates branch      Approved ✓
  Constraints        Plan Steps         Writes Files        or Revise ↩
```

## Architecture

### Roles

| Role | Model | Responsibility |
|------|-------|----------------|
| **Architect** | OpenAI (GPT-4o) | Transforms a raw request into structured goals, constraints, and success criteria |
| **Planner** | OpenAI (GPT-4o) | Converts the structured task into ordered, typed execution steps |
| **Executor** | Claude (Sonnet) | Creates a git branch, generates file content, writes files, commits changes |
| **Reviewer** | OpenAI (GPT-4o) | Evaluates the output against success criteria and decides: approved or revise |

### State Machine

```
pending
  └─▶ planning         (Architect enriches the task)
        └─▶ ready_for_execution  (Planner creates the plan)
              └─▶ executing      (Executor runs the plan on a branch)
                    └─▶ in_review        (Reviewer evaluates the output)
                          ├─▶ approved ─▶ complete   (GitHub push + optional PR)
                          └─▶ revise ──▶ executing   (Loop back, max 3 times)
                                                └─▶ failed (if max revisions exceeded)
```

### Directory Structure

```
ai-build-system/
├── runner.py             # Main runner — start with: python runner.py
├── submit_task.py        # Submit a new task
├── dashboard.py          # View task status dashboard
├── start.sh / start.bat  # One-command start scripts
│
├── tasks/                # Task packets (JSON) — one per task
├── plans/                # Plan packets — generated by Planner
├── artifacts/            # Execution results — generated by Executor
├── reviews/              # Review packets — generated by Reviewer
├── state/                # system_state.json (live runner state)
├── logs/                 # Phase logs + execution history + errors
├── prompts/              # System prompts for each AI role
├── schemas/              # JSON schema definitions for all packets
│
└── runner/               # Python package
    ├── config.py         # Configuration (reads .env)
    ├── logger.py         # Centralized logging
    ├── schemas.py        # Packet factories and file I/O
    ├── state_manager.py  # State machine transitions
    ├── pipeline.py       # Pipeline orchestrator
    ├── github_ops.py     # Git branch push + PR creation
    ├── dashboard.py      # Terminal dashboard (rich)
    └── roles/
        ├── architect.py  # Architect role (OpenAI)
        ├── planner.py    # Planner role (OpenAI)
        ├── executor.py   # Executor role (Claude)
        └── reviewer.py   # Reviewer role (OpenAI)
```

### Inter-Agent Communication

All agents communicate exclusively through structured JSON files — no direct function calls between roles:

| Packet | Location | Written by | Read by |
|--------|----------|------------|---------|
| Task Packet | `tasks/{task_id}.json` | User / Architect | Planner, Executor, Reviewer |
| Plan Packet | `plans/{task_id}.json` | Planner | Executor |
| Execution Result | `artifacts/{task_id}.json` | Executor | Reviewer |
| Review Packet | `reviews/{task_id}.json` | Reviewer | Pipeline |
| System State | `state/system_state.json` | Runner | Dashboard |

## Setup

### Prerequisites

- Python 3.10+
- Git
- OpenAI API key
- Anthropic API key
- `gh` CLI (optional, for PR creation)

### Installation

```bash
# 1. Clone the repo
git clone https://github.com/evhedric/ai-build-system.git
cd ai-build-system

# 2. Install dependencies
pip install -r requirements.txt

# 3. Configure environment
cp .env.example .env
# Edit .env and fill in your OPENAI_API_KEY and ANTHROPIC_API_KEY
```

### Configuration (`.env`)

| Variable | Required | Default | Description |
|----------|----------|---------|-------------|
| `OPENAI_API_KEY` | Yes | — | OpenAI API key |
| `ANTHROPIC_API_KEY` | Yes | — | Anthropic API key |
| `OPENAI_MODEL` | No | `gpt-4o` | Model for Architect/Planner/Reviewer |
| `CLAUDE_MODEL` | No | `claude-sonnet-4-6` | Model for Executor |
| `GITHUB_TOKEN` | No | — | GitHub token (needed for PR creation) |
| `GITHUB_REPO` | No | `evhedric/ai-build-system` | Target repository |
| `AUTO_CREATE_PR` | No | `false` | Auto-create PR on approval |
| `MAX_REVISIONS` | No | `3` | Max revision cycles per task |
| `POLL_INTERVAL` | No | `3` | Seconds between task scans |

## Usage

### Start the runner

```bash
# Windows
start.bat

# Linux / macOS / Git Bash
./start.sh

# Or directly
python runner.py
```

### Submit a task

```bash
# Submit inline
python submit_task.py "Generate a data model for a user authentication system"

# Submit with priority
python submit_task.py --priority high "Fix the login bug causing 500 errors"

# Submit from a file
python submit_task.py --file my_request.txt

# Interactive mode
python submit_task.py
```

### View the dashboard

```bash
# Show once
python dashboard.py

# Live refresh every 5 seconds
python dashboard.py --watch 5
```

### Other runner options

```bash
# Process all pending tasks once, then exit
python runner.py --once

# Validate your configuration
python runner.py --check-config

# Just show the dashboard
python runner.py --dashboard
```

## Workflow Example

1. **Submit a task:**
   ```bash
   python submit_task.py "Add input validation to the user registration endpoint"
   ```
   This creates `tasks/task-XXXXXXXX.json` with `status: pending`.

2. **Runner picks it up** (if already running) or run:
   ```bash
   python runner.py --once
   ```

3. **Pipeline executes:**
   - Architect → enriches task with goals and success criteria
   - Planner → creates ordered steps in `plans/`
   - Executor → creates branch `task/task-XXXXXXXX/...`, writes files, commits
   - Reviewer → evaluates output, approves or requests revision

4. **On approval:**
   - Task moves to `complete`
   - Branch is pushed to origin
   - PR is created (if `AUTO_CREATE_PR=true`)

5. **Check status:**
   ```bash
   python dashboard.py
   ```

## Known Limitations

- **No runtime code execution.** The Executor writes files; it does not run or test them. Generated code may contain syntax errors or logical bugs. Always review output before merging.
- **Context window constraints.** Very large tasks or plans with many steps may hit API token limits. Break large tasks into smaller, focused requests.
- **Single task at a time.** The runner processes one task through the pipeline sequentially. Parallel task execution is not currently supported.
- **Revision loops are capped.** If a task fails review three times (configurable via `MAX_REVISIONS`), it moves to `failed` state. You can resubmit with a more specific request.
- **Git operations require a clean working tree.** The Executor assumes it can create and switch branches. Uncommitted local changes may cause conflicts.
- **No secret scanning.** The system does not inspect generated file content for hardcoded credentials or sensitive data. Review artifacts before committing to shared repositories.

## Contributing

Contributions are welcome. To add a new agent role, swap an underlying model, or modify pipeline behavior:

1. Fork the repository and create a feature branch.
2. Role logic lives in `runner/roles/` — each role is a self-contained module.
3. System prompts live in `prompts/` and can be modified without touching Python code.
4. Run the test task after any pipeline change to verify end-to-end behavior.
5. Open a pull request with a clear description of the change and its intent.

Please do not commit real API keys or tokens. Use `.env` for all credentials.

## Design Principles

- **Local-first**: All state lives in files on disk. No database required.
- **Transparent**: Every decision is logged. Every artifact is inspectable.
- **Modular**: Each role is a single Python module — easy to swap models or logic.
- **Simple**: The runner is a polling loop. The pipeline is a straight function call chain.
- **Traceable**: Every state transition writes to the execution history log.
