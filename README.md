## Overview

Submit a task once. The system passes it through four specialized AI agents — each with a distinct role — until the work is complete and approved.

```
User Request
     │
     ▼
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  Architect  │───▶│   Planner   │───▶│  Executor   │───▶│  Reviewer   │
│  (OpenAI)   │    │  (OpenAI)   │    │  (Claude)   │    │  (OpenAI)   │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
  Goals &            Ordered            Creates branch      Approved ✓
  Constraints        Plan Steps         Writes Files        or Revise ↩
```

## Architecture

### Agent Roles

| Role | Model | Responsibility |
|------|-------|----------------|
| **Architect** | OpenAI (GPT-4o) | Converts a raw request into structured goals, constraints, and success criteria |
| **Planner** | OpenAI (GPT-4o) | Breaks the structured task into ordered, typed execution steps |
| **Executor** | Claude (Sonnet) | Creates a git branch, generates file content, writes files, and commits changes |
| **Reviewer** | OpenAI (GPT-4o) | Evaluates output against success criteria and decides: approve or request revision |

### State Machine

Tasks move through the following states:

```
pending
  └─▶ planning              (Architect enriches the task)
        └─▶ ready_for_execution   (Planner creates the plan)
              └─▶ executing       (Executor runs the plan on a branch)
                    └─▶ in_review         (Reviewer evaluates the output)
                          ├─▶ approved ─▶ complete    (Branch pushed + optional PR)
                          └─▶ revise  ──▶ executing   (Loop back, max 3 times)
                                                └─▶ failed (if max revisions exceeded)
```

### Directory Structure

```
ai-build-system/
├── runner.py             # Main entry point — start with: python runner.py
├── submit_task.py        # Submit a new task
├── dashboard.py          # View task status dashboard
├── start.sh / start.bat  # One-command startup scripts
│
├── tasks/                # Task packets (JSON) — one file per task
├── plans/                # Plan packets — generated by the Planner
├── artifacts/            # Execution results — generated by the Executor
├── reviews/              # Review packets — generated by the Reviewer
├── state/                # system_state.json (live runner state)
├── logs/                 # Phase logs, execution history, and errors
├── prompts/              # System prompts for each AI role
├── schemas/              # JSON schema definitions for all packet types
│
└── runner/               # Core Python package
    ├── config.py         # Configuration (reads .env)
    ├── logger.py         # Centralized logging
    ├── schemas.py        # Packet factories and file I/O
    ├── state_manager.py  # State machine transitions
    ├── pipeline.py       # Pipeline orchestrator
    ├── github_ops.py     # Git branch push and PR creation
    ├── dashboard.py      # Terminal dashboard (rich)
    └── roles/
        ├── architect.py  # Architect role (OpenAI)
        ├── planner.py    # Planner role (OpenAI)
        ├── executor.py   # Executor role (Claude)
        └── reviewer.py   # Reviewer role (OpenAI)
```

### Agent Communication

Agents do not call each other directly. Instead, they communicate by reading and writing structured JSON files:

| Packet | Location | Written By | Read By |
|--------|----------|------------|---------|
| Task Packet | `tasks/{task_id}.json` | User / Architect | Planner, Executor, Reviewer |
| Plan Packet | `plans/{task_id}.json` | Planner | Executor |
| Execution Result | `artifacts/{task_id}.json` | Executor | Reviewer |
| Review Packet | `reviews/{task_id}.json` | Reviewer | Pipeline |
| System State | `state/system_state.json` | Runner | Dashboard |

## Setup

### Prerequisites

- Python 3.10 or later
- Git
- OpenAI API key
- Anthropic API key
- `gh` CLI *(optional — only required for automatic PR creation)*

### Installation

```bash
# 1. Clone the repository
git clone https://github.com/evhedric/ai-build-system.git
cd ai-build-system

# 2. Install dependencies
pip install -r requirements.txt

# 3. Set up your environment
cp .env.example .env
# Open .env and add your OPENAI_API_KEY and ANTHROPIC_API_KEY
```

### Configuration

All configuration is managed through the `.env` file. The following variables are available:

| Variable | Required | Default | Description |
|----------|----------|---------|-------------|
| `OPENAI_API_KEY` | Yes | — | Your OpenAI API key |
| `ANTHROPIC_API_KEY` | Yes | — | Your Anthropic API key |
| `OPENAI_MODEL` | No | `gpt-4o` | Model used by the Architect, Planner, and Reviewer |
| `CLAUDE_MODEL` | No | `claude-sonnet-4-6` | Model used by the Executor |
| `GITHUB_TOKEN` | No | — | GitHub token (required for PR creation) |
| `GITHUB_REPO` | No | `evhedric/ai-build-system` | Target repository for pushes and PRs |
| `AUTO_CREATE_PR` | No | `false` | Automatically create a PR when a task is approved |
| `MAX_REVISIONS` | No | `3` | Maximum number of revision cycles allowed per task |
| `POLL_INTERVAL` | No | `3` | Seconds between task scans |

## Usage

### Start the Runner

```bash
# Windows
start.bat

# Linux / macOS / Git Bash
./start.sh

# Or run directly
python runner.py
```

### Submit a Task

```bash
# Submit a task inline
python submit_task.py "Generate a data model for a user authentication system"

# Submit with a priority level
python submit_task.py --priority high "Fix the login bug causing 500 errors"

# Submit from a file
python submit_task.py --file my_request.txt

# Launch interactive mode
python submit_task.py
```

### View the Dashboard

```bash
# Show the dashboard once
python dashboard.py

# Refresh automatically every 5 seconds
python dashboard.py --watch 5
```

### Additional Runner Options

```bash
# Process all pending tasks once, then exit
python runner.py --once

# Verify your configuration is valid
python runner.py --check-config

# Display the dashboard only
python runner.py --dashboard
```

## Workflow Example

The following example walks through a complete task from submission to approval.

1. **Submit a task:**
   ```bash
   python submit_task.py "Add input validation to the user registration endpoint"
   ```
   This creates `tasks/task-XXXXXXXX.json` with `status: pending`.

2. **Run the pipeline** *(if the runner is not already running)*:
   ```bash
   python runner.py --once
   ```

3. **The pipeline executes in order:**
   - **Architect** — Enriches the task with goals and success criteria
   - **Planner** — Creates an ordered list of steps in `plans/`
   - **Executor** — Creates a branch (`task/task-XXXXXXXX/...`), writes files, and commits
   - **Reviewer** — Evaluates the output and either approves it or requests a revision

4. **On approval:**
   - The task status moves to `complete`
   - The branch is pushed to the remote
   - A PR is created automatically if `AUTO_CREATE_PR=true`

5. **Check the task status:**
   ```bash
   python dashboard.py
   ```

## Logs

All activity is written to the `logs/` directory. Each role has its own log file for easy debugging.

| File | Contents |
|------|----------|
| `logs/runner.log` | Main runner activity |
| `logs/architect.log` | Architect role traces |
| `logs/planner.log` | Planner role traces |
| `logs/executor.log` | Executor role traces |
| `logs/reviewer.log` | Reviewer decisions |
| `logs/github.log` | Git and GitHub operations |
| `logs/execution_history.log` | Structured event log for all tasks |
| `logs/errors.log` | All errors with task context |

## Design Principles

| Principle | Description |
|-----------|-------------|
| **Local-first** | All state is stored in files on disk. No database is required. |
| **Transparent** | Every decision is logged and every artifact can be inspected. |
| **Modular** | Each agent role is a single Python module, making it easy to swap models or update logic. |
| **Simple** | The runner is a polling loop. The pipeline is a straightforward chain of function calls. |
| **Traceable** | Every state transition is recorded in the execution history log. |
